The process behind these steps is described in [Release Cycle](./release_cycle.md). 

This examples describes the release of `v0.8.0`.

## Cut a release branch

Requires `gh`, `cargo` and `uv`.

```bash
cd mosaico

git switch main && git pull
scripts/release-cut
```

The script opens a pull request that bumps `main` to `0.9.0-dev`. 
Merging the generated PR will trigger a workflow that creates `release/v0.8` with `mosaicod` and the SDK at `0.8.0-rc`.

## Release mosaicod or the Python SDK

In GitHub, open **Actions → Release → Run workflow**, select the `release/v0.8` branch and the component. Or from the terminal:

```bash
gh workflow run release.yml --ref release/v0.8 -f component=mosaicod
gh workflow run release.yml --ref release/v0.8 -f component=python
```

The workflow moves the component from `0.8.0-rc` to `0.8.0`, tags that commit (`v0.8.0` for mosaicod, `py/v0.8.0` for the SDK), then moves `release/v0.8` to `0.8.1-rc`. It creates the GitHub release of the tag, with the changelog generated by `scripts/workflows/changelog.sh` as its text. For mosaicod, it also starts the builds of the binaries and the container image; for the SDK, the build of the wheel. The binaries and the wheel are attached to the GitHub release.

Patch and incremental releases work the same way: run the workflow again.

## Backport a change

```bash
git fetch origin
git switch -c backport/<issue>-v0.8 origin/release/v0.8
git cherry-pick -x <commit>
gh pr create --base release/v0.8
```

## Publish the documentation

```bash
git switch release/v0.8 && git pull
git tag -f doc/v0.8
git push -f origin doc/v0.8
```

Run it again after every documentation change on `release/v0.8` to move the tag forward.
